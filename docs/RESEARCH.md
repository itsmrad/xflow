# Research record

Reviewed 2026-09-30. This is a dated assessment of primary sources, not a claim that XFlow has shipped the referenced features. Official help pages can change, and Firecrawl returned some cached pages from September 28–29. The upstream code assessment is pinned to whisrs commit `b9584a0aad7fba393336246619d3987e2f03e6d4` (package version 0.1.27). No upstream performance claims were reproduced by a local benchmark.

## Wispr Flow: product and operating behavior

The current [product page](https://wisprflow.ai/) presents dictation across Mac, Windows, iPhone and Android: multilingual recognition, punctuation, filler removal, backtracking, vocabulary, snippets and style adaptation. It now also markets a meeting notetaker. XFlow focuses on desktop dictation; meetings, mobile keyboards, accounts and enterprise administration are outside the initial product. The advertised typing-speed comparison is a vendor claim, not an XFlow target or measured baseline.

The [Linux and terminal guide](https://docs.wisprflow.ai/articles/6478598909-using-flow-with-linux-wsl-and-terminal-applications) explicitly says there is no native Linux application. It documents paste recovery, Accessibility requirements on Mac, terminal formatting hazards and clipboard restoration limits. This supports a native Linux opportunity, but also shows why producing a transcript and successfully inserting it must be separate outcomes. XFlow should retain recoverable output when paste fails and never claim destination delivery solely because an input command returned successfully.

The [shortcut guide](https://docs.wisprflow.ai/articles/2612050838-supported-unsupported-keyboard-hotkey-shortcuts) documents hold-to-talk, hands-free, command, copy/paste-last and cancel actions. Custom shortcuts are per device, with reserved-combination and overlap restrictions. Hold-to-talk requires reliable release events; configuring an activation-only desktop shortcut does not provide that capability. XFlow must advertise toggle-only operation when its selected adapter cannot observe release.

The [dictionary guide](https://docs.wisprflow.ai/articles/4052411709-teach-flow-your-words-with-the-dictionary) distinguishes vocabulary from explicit misspelling replacement. Desktop replacement uses whole-word matching, prefers longer overlapping phrases, and preserves saved spelling. It notes that literal replacements are not language-aware. XFlow should likewise distinguish probabilistic provider hints from deterministic user corrections, with boundaries and language scoping before broad rollout.

The [snippet guide](https://docs.wisprflow.ai/articles/5784437944-create-and-use-snippets) describes spoken triggers expanding static saved text, including longest-match and personal-over-shared precedence. Rich formatting depends on destination capability. Its Android guidance explicitly carries a shipped-version verification caveat. XFlow will initially design plain-text, explicit user-managed expansions; account sync and rich text are unnecessary for a reliable first slice.

The [style guide](https://docs.wisprflow.ai/articles/2368263928-how-to-setup-flow-styles) describes categories inferred from app and, on desktop, web address, with capitalization/punctuation preferences. Its English-only notices and Android source-versus-release caveat narrow the marketing claim. XFlow should report unknown context rather than infer a writing style from an unavailable app identifier.

The [cleanup guide](https://docs.wisprflow.ai/articles/4283510616-auto-cleanup-control-how-much-flow-edits-your-dictation-beta) exposes None, Light and Medium, with Light the unset default and exceptions for very short/long text. XFlow instead uses raw/light/polished terminology and defaults to raw to make additional transformations and network calls explicit. Raw means no XFlow rewrite; an STT model may still supply punctuation or normalize speech.

The [command-mode guide](https://docs.wisprflow.ai/articles/4816967992-how-to-use-command-mode) describes paid desktop instruction-driven edits and search commands, with English spoken triggers and incomplete iOS editing. It notes existing text is required for edits and some failed edits have no error. XFlow's later selected-text transforms must have explicit selection, destination and error outcomes; dictation must never implicitly become a shell executor.

## Wispr Flow: privacy boundaries

The [Data Controls page](https://wisprflow.ai/data-controls), last updated August 18, 2026, separates model-improvement consent from cloud storage. It states transcription always occurs in the cloud, context awareness can send active-window text, app/textbox information contributes to formatting, usage statistics may still be collected, and auto-add monitors the destination textbox for spelling edits. It also describes third-party retention/training agreements and a notetaker exception for certain features.

The [privacy overview](https://wisprflow.ai/privacy) describes certification and enterprise controls. These are vendor representations; XFlow cannot inherit certifications or zero-retention agreements merely by calling a provider API. For BYOK, the user's provider account policy applies. XFlow's product commitment is narrower and auditable: local settings/history, no telemetry implementation, no default audio persistence, no transcript/secret logs, opt-in context acquisition, and fail-closed offline selection until a local backend exists.

Auto-learning remains design-only. Monitoring an entire application or learning arbitrary rewritten paragraphs is unnecessary and creates privacy and correctness risks. The proposed bounded observation design is in [ARCHITECTURE.md](../ARCHITECTURE.md).

## Verified provider and platform contracts

[Groq speech-to-text documentation](https://console.groq.com/docs/speech-to-text) specifies multipart upload to `/openai/v1/audio/transcriptions`, model selection, optional ISO-639-1 language and prompt hints, and JSON/text/verbose JSON output. Direct attachments are limited to 25 MB, while higher-tier URL input can differ. Minimum billed duration is 10 seconds. These are API constraints, not measured speed guarantees; repeated small pseudo-streaming uploads change cost and semantics.

[OpenRouter create-transcription reference](https://openrouter.ai/docs/api/api-reference/stt/create-transcription) specifies `/api/v1/audio/transcriptions` with JSON `input_audio` containing base64 `data` and `format`, plus `model` and optional `language`. The documented response contains `text` and optional usage. This must be a distinct adapter from Groq's multipart format. A configurable URL alone cannot make an arbitrary HTTP or WebSocket service OpenAI compatible.

The official [GlobalShortcuts portal reference](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html) defines sessions and Activated/Deactivated signals. That specification does not establish availability on every installed desktop/version. Probe the actual backend, fall back to desktop bindings/CLI, and test release semantics before enabling push-to-talk. GNOME Shell extension, wlroots, KDE, X11 and future macOS adapters need separate integration tests.

## Decisions and unresolved evidence

The integrated initial slice targets Ubuntu GNOME with batch STT, explicit recovery and a tiny native overlay. Fedora, macOS, compositor-native streaming injection, richer context and personalization follow only after platform-specific verification. The [headless report](benchmarks/linux-headless.json) measures startup, idle process usage and status IPC under a short synthetic workload; it does not measure microphone, live provider, hotkey, text injection or overlay behavior. Live provider credentials, physical microphone capture, actual destination delivery, direct uinput behavior, true GNOME press/release hotkeys, overlay lifecycle and shell-frame cost still require desktop acceptance; source review and mocked tests cannot establish them.
